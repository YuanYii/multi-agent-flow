# AGENTS.md - 多专家团队协同研发工作区

欢迎来到 **多专家协同研发工作流 (Multi-Agent Team Workflow · YY-Flow)** 工作区。本文档定义了 AI Agent 在多角色研发环境下的交互契约与协作红线。

---

## 统一入口网关与任务分级前置门控 (Gateway & Tiering Gate)

当收到用户的业务研发需求、自然语言对话或代码变更指令时，Agent **必须优先执行分级前置门控**：
1. **控制台指令直通**：若为 `/yy-flow start/status/kanban/sync-pr/gate` 等运维指令，直接分发执行底层脚本；
2. **业务需求强制分级三问**：其他所有业务指令强制执行分级三问，并在**回复首行显式输出结构化标识**：
   - `【任务分级: L0 即时问答】`：纯会话咨询/无仓库修改，无卡直接输出解答（0 CLI 脚本延迟）；
   - `【任务分级: L1 轻量任务】`：单人单步/文档或微调，自动创建 B/C/D/F/G 类任务卡走短链，由 PM 终态验收；
   - `【任务分级: L2 标准研发】`：核心业务逻辑/多角色协作/公共库变更，自动创建 A 类任务卡走全链（DEV→Reviewer→QA→PM）；
3. **执行态 Task ID 豁免**：若指令已包含明确 Task ID（如 `T0001`）或属于子代理执行内部流转，直接推进状态机，**严禁二次重复建卡**；
4. **核心模块强制升格 L2**：涉及公共核心库、鉴权安全、数据库变更的代码修改，即使单文件亦强制升格为 L2 全流程。

## 快捷指令响应契约 (/yy-flow)

当收到以 `/yy-flow` 开头的用户指令时，Agent 必须直接触发对应的确定性动作：
- `/yy-flow` 或 `/yy-flow start` -> 立即执行初始化 7 步 SOP 并拉起 PM 严经理；
- `/yy-flow status` -> 运行 `heartbeat.py` 巡检脚本，输出全局大盘进度条、交付周期与告警；
- `/yy-flow kanban` -> 后台启动 `start_kanban_server.py`（默认不带 `--port`，自动探测/复用），展示 Web 看板访问链接与大盘；
- `/yy-flow sync-pr` -> 运行 `sync_pr_status.py` 扫描【已阻塞】任务卡，检测 GitHub PR Merged 自动推进至【已完成】并唤起 PM 验收；
- `/yy-flow auto <需求>` -> 端到端全自动多专家研发流水线：由主 Agent / PM 严经理串行调度多专家子代理（`flow-dev` ➔ `flow-reviewer` ➔ `flow-qa`）完成实体代码开发与测试，到达【已完成】主动停机交付（严禁 Agent 代签验收；最多允许打回自愈 2 轮；代码保留在工作区，严禁擅自 git commit）；
> [!IMPORTANT]
> **跨平台 Python 解释器执行红线**：AI Agent 在调用 `run_command` 执行任何工作流 CLI 脚本时，必须根据宿主操作系统自适应前缀：**Linux/macOS 使用 `python3`，Windows 环境必须使用 `python`**，严禁硬编码导致命令找不到。
>
> **工单列表打印精简原则**：在聊天窗口回复或 CLI 工具输出工单大盘列表时，**严禁全量倾倒所有工单**；默认**只打印最新倒序的 5 条工单记录**（最近创建或流转的任务排在前），其余数据引导用户访问 Web 页面查看，避免刷屏与过度消耗 Token。

## 看板状态不变量

- **原子更新**：看板 `状态` (Status) 与 `处理人` (Assignee) 必须同步变更。
- **结束时间**：任务推至 `已完成` / `已验收` 前强制写入 `结束时间`。
- **终态锁定**：已处于 `已验收` 或 `已取消` 终态的任务禁止逆向流转回中间状态。

## 团队协作 10 大红线 (Red Lines)

1. **绝对禁止越权修改状态**：不在操作人集合内的角色禁止推动状态（提权需显式声明代行协议）。
2. **打回绝对禁止新建任务编号**：任何审查/测试退回必须在**原任务**上改状态为 `已退回`，并在备注写入 `DEF-TXXX-N`，严禁通过作废旧卡新建新卡逃避打回审计。
3. **绝对禁止先干后补与秒级冲卡**：自领取任务时，必须先将看板状态修改为 `进行中` 并落盘真实开工时间，方可开始编码；严禁事后批量补卡或在同一秒内无时间差连续推进 4~5 个流转节点，确保交付周期 (Lead Time) 真实可信。
4. **绝对禁止生成孤儿复审/复测报告**：退回修复后的结论必须追加至原报告，不新建碎片文档。
5. **绝对禁止无元数据乱建深层文档与擅改原文档**：工程文档路径深度不得超过 3 级，所有 `.md` 强校验 YAML Frontmatter 标头，过程草稿统一入 `草稿箱/` 隔离；初始化归档原项目历史文档时采用**只读镜像拷贝**，绝对禁止修改、覆盖或删除原项目源文档中的任何内容。
6. **Subagent 官方标准路径实时查证原则**：初始化或挂载 Subagent 时，必须查证当前 Agent 官方最新文档，获取其原生识别子代理的物理路径与 YAML 标头规范（如 Antigravity 的 `{workspace}/.agents/agents/{name}/agent.md`），严禁凭猜测写入异构不合规路径。
7. **虚拟专家身份与外部通信铁律**：8 大专家角色均为系统虚拟 AI 子代理，系统内流转以**看板任务卡**（`transition_task.py`）与子代理总线（`invoke_subagent`）为唯一法定通知通道；**严禁**调用外部通讯录接口（飞书/钉钉/企业微信等）搜索虚拟角色人名发起私聊。
8. **无工单绝对禁止执行 Git 提交与 PR 追更擅自拆单（内外隔离）**：执行 `git commit`、`git push` 或发起 PR 前，内部必须有明确的看板活跃工单承载；外部 Commit Message 与 PR 正文严格保持纯净通用，严禁注入内部任务编号（如 T00xx）与虚拟专家人名；响应 PR Review 追更时必须沿用原工单打回流转，严禁新建碎片工单。
9. **绝对禁止物理删除看板任务与直接篡改底层 board.json**：看板任务全生命周期只增不减，绝对禁止使用任何文本编辑工具（`replace_file_content` / `write_to_file`）或脚本直接修改/删除 `board.json` 文件；作废任务必须由 PM 严经理（或授权代行）调用 `quick_task.py complete` 流转至【已取消】终态归档。
10. **绝对禁止终态逆流篡改**：已达到【已验收】或【已取消】终态归档的工单，禁止逆向流转为【进行中】、【审查中】或【已阻塞】。
11. **绝对禁止代行人类验收（人类专属终态红线）**：任何 Agent 严禁调用 `quick_task.py accept` / `accept-all`，严禁以任何形式传入 `--delegated-by USER`、伪造 `role=USER` 或推动任务进入【已验收】终态；自动化与代行流转只允许声明 `PM` 来源（或省略），到【已完成】即停并提请人类用户验收。验收合法通道仅为：Web 看板主控 Token 操作，或真人终端执行 accept（自带 TTY 检测 + [y/N] 确认）。

## 极简特权通道（Fast-Track）协议

并非所有任务都需要完整的 SDLC（软件生命周期）。系统启用极简通道机制：
1. **触发标识**：任何标题前缀为 `[HOTFIX]`、`[DOCS]` 或打上 `ASS`（极简任务）标签的任务。
2. **免检放行**：此类任务属于文档勘误、纯配置修改或紧急非代码操作。协调者（PM）分配执行后，无需经过 Reviewer 审查和 QA 测试，执行方完成后可直接将状态流转为 `已完成/已验收`。
3. **红线拦截**：绝不允许任何涉及业务代码逻辑（`.py`, `.java`, `.ts` 等核心源码）的修改挂载此标签。一旦发现越权，协调者应立即阻断并剥夺其极简标签。
4. **通道区分**：`[HOTFIX]` 特权通道允许跳过 PM 直接验收；而 **L1 轻量任务** 走标准短链（待开始→进行中→已完成→已验收），仍需由 PM 进行终态验收。

## 分派即建单协议 (Dispatch-on-Create)

> 核心原则：**看板任务卡是唯一事实来源，任何会产生文件、仓库变更或可追溯结论的任务必须先有卡，再被执行（L0 即时问答除外——分级三问见 references/02 §任务分级）。**

### 任务分级与单一职责前置双判定 (L0/L1/L2 & SRP)
PM / 主代理在派发任务与建卡前，强制执行“分级三问与单一职责”双重判定：
1. **分级三问**：
   - 会留下文件/仓库变更吗？否 → **L0 即时问答**（直接作答、不调用 CLI、不建卡；L0 无卡不违规）；
   - 留下的东西需要事后追溯吗？否 → **L0**；是 → **L1 轻量任务**（类型 B/C/D/F/G，建卡走短链：待开始→进行中→已完成→已验收）；
   - 需要多角色协作或动核心资产吗？是 → **L2 标准任务**（类型 A，建卡走全链：待开始→进行中→审查中→测试中→已完成→已验收）。
2. **单一职责 (SRP) 四维度前置自检**：
   - **单角色**：是否仅限 1 位专职专家？
   - **单交付物**：产出物形态是否单一（1 份 ADR / 1 组 API 及单测 / 1 个前端组件 / 1 份测试用例）？
   - **工时上限**：单卡预估工时是否 ≤ 8.0h（超限必须建立工作包并细分子任务链）？
   - **三必拆原则**：凡涉及新增数据库表、新增/重构接口、新增前端独立页面，**必须拆分为独立原子卡片**，严禁单卡承接全栈复合需求。

### 建单履约流转规约
1. **建卡前置**：主代理（或任一角色）在分派 L1/L2 任务 / 唤起子代理之前，必须先调用建单命令创建任务卡【待开始】并获取 Task ID（L0 免建卡）：
   ```bash
   python3 scripts/quick_task.py create --name "<任务名称>" --role PM --assignee <处理人> --type <类型> --remarks "<核心要点>"
   ```
2. **Task ID 注入**：子代理 Prompt 顶部必须强制注入工单元数据标头（L0 除外）：`【任务卡】Task ID: T000x | 状态: 待开始 | 处理人: <处理人>`
3. **开工前建卡/领单硬门禁**：凡涉及任何文件创建、修改或删除的任务（L1 短链 / L2 全链），在动手改动任何代码或文档前，第一步必须执行 `--create` 建卡并领取为【进行中】；严禁“无卡改文件”（Fail-Closed）。仅不修改任何项目文件的纯文本即时咨询（L0 级）允许免卡直答。
4. **Git 动作三步闭环门禁**：
   - **前置锁定**：执行 `git commit`/`push` 前确保内部工单已在【进行中】；
   - **纯净提交**：Commit Message 与 PR 遵循标准通用格式，严禁出现内部任务编号与虚拟专家人名；
   - **挂起与解阻**：发起 PR 后将工单推至【已阻塞】（释放并发，内部备注记录 PR 链接）；外部 PR 合流后由用户主动触发解阻推至【已完成】，最后交由 PM 严经理验收。
5. **完工后流转闭环硬门禁**：任何代码/文档/审查/测试产出完成后，最后一步必须执行流转 CLI 推进状态（A 类推至【审查中】，B/C/D/G 类推至【已完成】并记录 `end_time`），否则视为未交付。
6. **防重复建单**：建卡前若看板最近 N 条任务存在名称重复，命令将终止并输出 `DUPLICATE_TASK` 候选；需用户确认后以 `--force` 重跑。
7. **任务卡必经【待开始】**：不允许直接创建为【进行中】或更高状态，必须经历生命周期完整流转。
8. **单一任务原则 (Single Responsibility Principle, SRP) 物理前置门禁**：
   - 一张任务卡必须且仅能由一位专属专家负责，产出单一形态的原子交付物（如 1 篇 ADR / 1 组 API 及单测 / 1 个前端组件 / 1 套回归用例）；
   - 严禁创建跨架构、前后端、测试的大杂烩复合任务（如*“设计方案并开发前后端页面且写测试”*）；
   - PM 严经理在 WBS 分解时必须按工作包输出原子任务；CLI 与 REST API 前置校验违规复合任务将直接拒绝建卡（Fail-Closed），特殊情况需以 `--force` 显式覆盖并在审计日志打标。

## 界面与文档视觉扁平化规范 (Visual & Design Specification)

- **严禁使用拟真/3D 图标 (No Skeuomorphic/Realistic Icons)**：所有前端页面、Web 组件、可视化看板与文档展示中，**严禁使用 3D 拟真 Emoji、厚重拟物投影或具象拟真图标**（如 🌊、👔、🚀、📦 等 3D 彩色表情符号）。
- **全量采用现代极简扁平化设计 (Strict Flat Vector Design)**：
  1. 统一采用**扁平化矢量 SVG 路径**、精炼几何线性/双色面性图标，保持工业级软件界面的克制、清爽与专业度；
  2. 颜色采用统一的设计 Token 变量（如 `var(--ink)`, `var(--cyan)`, `var(--accent-light)` 等），严禁无序的多彩拟物混杂；
  3. 图标比例保持对齐与内边距统一（标准 `viewBox="0 0 24 24"`，`stroke-width="2"` 线性描边或简洁纯色扁平填充）。

## 10. Word (DOCX) 文档排版与学术论文规范标准

在生成或编辑**未提供特定模板的 Word (`.docx`) 方案书、技术报告、白皮书或交付物文档**时，必须严格按照**学术论文与技术报告国家标准（GB/T 7713）**规范进行排版：

1. **中西文字体强制搭配**：
   - **正文与表格数据**：**宋体 (SimSun) + Times New Roman**
   - **各级标题与表头**：**黑体 (SimHei) + Times New Roman**
   - **作者信息/摘要/注释**：**楷体 (KaiTi) + Times New Roman**
   - **底层 XML 绑定要求**：生成 OpenXML / `python-docx` 时，必须显式在每个 Run 的 `rFonts` 中强绑定 `w:eastAsia`、`w:ascii`、`w:hAnsi` 与 `w:cs`，严禁遗漏 `w:eastAsia` 导致汉字静默回退为不同字体或字号不一。
2. **标准学术五级字号与行距体系**：
   - **文档大标题**：小二号 (18pt) 黑体 加粗 居中（段前 14pt，段后 4pt）
   - **一级标题 (一、/ 1.)**：四号 (14pt) 黑体 加粗（段前 14pt，段后 6pt）
   - **二级标题 (2.1 / 1.1)**：小四号 (12pt) 黑体 加粗（段前 10pt，段后 4pt）
   - **正文段落**：五号 (10.5pt) 宋体，**标准 1.3 倍学术行距**（段前 3pt，段后 3pt）
   - **表格表头**：小五号 (9.5pt) 黑体 加粗 居中，背景浅灰蓝 `#F1F5F9`
   - **表格内容**：小五号 (9.0pt) 宋体，1.15 倍行距，首列关键字段加粗 `#F8FAFC`
3. **标准 A4 页面边距**：
   - 页边距统一设置为：上 2.54 cm (1.0 inch)，下 2.54 cm (1.0 inch)，左 2.80 cm (1.1 inch)，右 2.80 cm (1.1 inch)。
