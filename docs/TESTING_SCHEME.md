## 一、 测试体系概述与设计目标

为保障 multi-agent-flow 在多专家并发交互、局域网协作、状态机长链流转以及数据持久化过程中的健壮性与完整性，本测试方案构建了**双层质量保障体系**：
1. **单元与 API 基础功能测试（244 项基准用例）**：验证 HTTP 路由响应、查询筛选、白名单校验、双层文件锁排他并发以及 RBAC 鉴权拦截；
2. **108 任务全正交仿真与数据质量审计引擎**：在独立沙箱环境中模拟真实生产全周期，覆盖所有阶段、角色、状态、极值工时、边界字符以及越权对抗，并由审计引擎对落盘数据执行 8 大维度的严格一致性断言。

## 二、 108 任务高离散度全正交矩阵结构

整个测试任务集（`T0001` ~ `T0108`）划分为 4 大工程矩阵，确保集中度低、离散度高、数学组合全覆盖：

```
┌────────────────────────────────────────────────────────────────────────┐
│               108 任务全正交工程矩阵体系 (High-Dispersion Matrix)      │
├────────────────────────────────┬───────────────────────────────────────┤
│ 矩阵一: 8 阶段 × 9 状态全覆盖   │ 72 条 (T0001~T0072) 全笛卡尔积正交铺满 │
│ 矩阵二: 多专家跨角色深度协同   │ 16 条 (T0073~T0088) 多跳返工与长链追溯 │
│ 矩阵三: 工时极端值与边界防御   │ 8 条 (T0089~T0096) 极端数值/XSS/长文本 │
│ 矩阵四: 局域网权限与并发对抗   │ 12 条 (T0097~T0108) 受控写/并发/403拦截│
└────────────────────────────────┴───────────────────────────────────────┘
```

### 1. 矩阵一：阶段 × 状态全笛卡尔积网格 (72 任务, T0001 ~ T0072)
- **8 大阶段**：S1 需求分析、S2 架构设计、S3 编码实现、S4 单元测试、S5 代码审查、S6 工作流集成测试、S7 文档编制、S8 运维部署；
- **9 大状态**：`待开始`、`进行中`、`审查中`、`测试中`、`已完成`、`已验收`、`已退回`、`已阻塞`、`已取消`；
- **覆盖保障**：确保 8 大阶段中的每一个阶段在 9 种状态中均有且仅有 1 个独立样本，避免任何状态盲区。

### 2. 矩阵二：多专家跨角色复杂协同与返工网格 (16 任务, T0073 ~ T0088)
- **多跳返工链路**：
  - 前端审查退回修复（马前端 $\leftrightarrow$ 周审查 $\rightarrow$ 章测试 $\rightarrow$ 严经理）；
  - 3 轮严苛代码审查打回返工（周审查 连续 3 次打回 李开发，追溯链长达 11 节点）；
  - 2 轮集成测试严重缺陷打回（章测试 连续 2 次打回修复）；
  - 多角色大闭环协同（需求/架构/开发/审查/测试/文档/运维 4~8 角色接力流转）；
  - 角色代号自动归一化验证（输入 `dev/fe/cr/qa/pm` 自动归一化为中文名）。

### 3. 矩阵三：工时极端值与数据边界防御网格 (8 任务, T0089 ~ T0096)
- **工时极值**：0 工时极速热修任务（0.0h）、0.1h 极小工时微任务、150h 跨季度超大工时、严重超支 700% 任务；
- **字符防御**：XSS 注入防御（`<script>alert(1)</script>` 标签与属性）、Emoji 表情与国际化 Unicode 字符（🎉, ⚡, こんにちは）、复杂多行 Markdown 混排语法、1500 字符超长过程日志。

### 4. 矩阵四：局域网权限受控写与 403 越权对抗网格 (12 任务, T0097 ~ T0108)
- **4 项合法受控写**：协作者（无 Token）更新实际工时 `act_hours`、追加备注 `remarks`、流转常规状态以及多线程高频并发写；
- **8 项越权强拦截（严格断言 HTTP 403）**：
  - 越权 POST `/api/tasks`（新建任务）；
  - 越权 DELETE `/api/tasks/{id}`（删除任务）；
  - 越权 POST `/api/tasks/{id}/transition` 至【已验收】终态；
  - 越权 POST `/api/tasks/{id}/transition` 至【已取消】终态；
  - 越权 PUT `/api/tasks/{id}` 篡改核心字段（`name`, `assignee`, `stage`, `wp` 等）；
  - 越权 PUT `/api/tasks/reorder`（批量重排序）；
  - 越权 PUT `/api/board/meta`（修改偏好与看板标题）；
  - 越权 POST `/board.json`（全量 JSON 覆写）。

## 三、 数据质量与一致性 8 大审计维度规范

仿真测试跑批完成后，审计引擎对 `board.json` 与 `audit_trail.log` 执行以下 8 项严格检验：

| 审计维度编号 | 维度名称 | 断言与检验规则 |
| :---: | :--- | :--- |
| **维度 1** | **任务标识唯一性 (ID Integrity)** | 全量任务 ID 严格匹配正则 `^T\d{4}$`，`len(cards) == len(set(ids))`，无重复或格式漂移。 |
| **维度 2** | **排序序号单调性 (Seq Monotonicity)** | `seq` 严格为连续正整数集合（`1 ~ N`），无跳号、断号或负值。 |
| **维度 3** | **状态机处理人映射规范 (Handler Mapping)** | 严格校验角色责任归属：`审查中` $\rightarrow$ 周审查；`测试中` $\rightarrow$ 章测试；完成态/终态（`已完成`/`已验收`/`已取消`） $\rightarrow$ 严经理；其余状态与分配负责人一致。 |
| **维度 4** | **时间周期逻辑性 (Timeline Ordering)** | 处于完成态/终态的任务必须具备合法的 `end_date`，且 `start_date` $\le$ `end_date`；非完成态任务 `end_date` 必须为空字符串。 |
| **维度 5** | **工时数值有效性 (Duration Validity)** | `est_hours >= 0.0` 且 `act_hours >= 0.0`，数值必须为非负有效浮点数，无 `NaN` 或非法类型。 |
| **维度 6** | **过程追溯连续性 (Process Continuity)** | 任务过程记录必须严格以 `[Txxxx-N01]` 为首节点，后续流转严格按 `N02, N03...` 连续递增，且节点内时间戳保持单调递增。 |
| **维度 7** | **审计日志双向一致性 (Audit Log Alignment)** | `board.json` 中的全部状态变更与写入事件，必须在 `audit_trail.log` 中检索到对应记录（包含操作人、三态终端标签与时间戳）。 |
| **维度 8** | **安全红线拦截合规性 (RBAC Redline Pass)** | 全部 8 项越权攻击测试必须全部返回 `403 Forbidden`，且未在数据文件中留下脏数据。 |

## 四、 自动化测试执行与使用指引

### 1. 执行授权与前置门禁规范 (Mandatory Authorization Gate)
- **硬性红线**：本测试体系（包含 108 任务全正交仿真测试与数据质量审计 `scripts/run_108_tasks_simulation.py`）属于大型自动化跑批与深度质量审计行为；
- **授权前置**：在每次执行本测试体系之前，**必须显式向决策者说明测试目标、矩阵范围与沙箱隔离策略，并获得用户明确发出的授权指令（如“确认执行”、“开始测试”等）后方可运行**；
- **严禁私自触发**：严禁任何 AI Agent 或自动化流程在未经用户明确授权的情况下私自、隐式或默认启动该测试体系。

### 2. 执行全量 108 任务仿真与数据质量审计
```bash
# 经用户显式授权后，执行仿真跑批并在终端输出 8 大维度审计结果与耗时统计
python3 scripts/run_108_tasks_simulation.py
```

### 3. 执行既有单元与 API 集成测试回归
```bash
# 运行 pytest 测试套件（包含 244 项断言用例）
PYTHONPATH=scripts pytest tests/ -q
```

## 五、 后续系统重大调整时的测试方案扩充指南

当后续对 multi-agent-flow 系统进行重大演进时，必须在当前测试方案的基础上进行相应扩充，具体扩充规范如下：

```
                    ┌────────────────────────────────────────┐
                    │      后续系统架构演进触发测试扩充      │
                    └───────────────────┬────────────────────┘
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
【新增业务阶段 / 角色】           【新增状态机状态节点】           【新增鉴权维度 / 路由】
  • 扩展矩阵一阶段笛卡尔积        • 扩展状态正交切片               • 扩展矩阵四合法受控写白名单
  • 在矩阵二增加新专家协同用例    • 更新维度 3 处理人映射规则      • 增加对应越权 403 攻击断言
  • 重新平衡总体任务容量 N        • 更新维度 4 终态时序规则        • 保持全维审计覆盖
```

### 1. 扩充场景一：新增业务研发阶段（如 S9 安全渗透 / S10 运营度量）
- **矩阵一更新**：按 $N_{new} = (\text{阶段数} + 1) \times 9$ 扩充正交网格，为新阶段铺满 9 大状态样本；
- **矩阵二更新**：在复杂流转网格中增加新阶段与既有阶段的交接流转（如 `S8 运维部署` $\rightarrow$ `S9 安全渗透` 打回）。

### 2. 扩充场景二：新增或调整任务状态（如 增加“挂起中”或拆分终态）
- **状态机更新**：在矩阵一与矩阵二中引入新状态流转步骤；
- **审计规则同步**：在 `run_108_tasks_simulation.py` 的维度 3（`Handler Mapping`）与维度 4（`Timeline Ordering`）中配置新状态的处理人规则与 `end_date` 约束。

### 3. 扩充场景三：新增敏感 API 路由或字段级权限
- **矩阵四更新**：
  - 若属于协作者合法字段，在受控写列表中添加字段修改断言（预期 200）；
  - 若属于主控专属保护路由/字段，在 403 攻击列表中添加对应越权调用断言（预期 403）。
- **审计规则同步**：同步更新维度 8 的断言计数器（如由 8 项提升至 $M$ 项）。

### 4. 扩充执行规范
- 任何新增测试用例均应遵循**沙箱隔离原则**，使用 `tempfile` 生成独立数据沙箱；
- 每次扩展后，全量仿真脚本与 `pytest` 回归套件必须全部达到通过状态，方可准入合并。
