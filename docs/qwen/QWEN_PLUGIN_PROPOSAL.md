## 一、 服务谁 (Persona 用户画像)

### 1. 目标角色与组织规模
- **目标用户**：中小型科技公司研发负责人 (Tech Lead)、敏捷项目经理 (Scrum Master / PM)、全栈工程师及使用 AI 编程助手进行端到端开发的独立开发者；
- **团队规模**：1 ~ 50 人研发团队；
- **常用工具**：Git、GitHub/GitLab、VS Code/Cursor、千问办公客户端、终端 CLI。

### 2. 核心痛点 (Pain Points)
1. **传统单 Agent 盲目生成与“点 YES 疲劳”**：单 Agent 既当裁判又当运动员，动辄生成数百行代码，人类精力有限无法逐行审阅，只能盲目 Accept，带入隐藏 Bug；
2. **缺乏状态机约束与越权篡改风险**：单 Agent 拥有全量权限，容易随意更改核心配置、跳过测试环节直接合流；
3. **秒级虚假流转与黑盒交付**：单 Agent 在 1 秒内推向完成，缺乏真实的时序执行与独立测试报告，后期排查成本极高；
4. **缺乏代码级硬门禁与人工验收卡点**：未经人类核验的代码极易被误提交到主分支。

### 3. 成功指标 (Success Metrics)
- **研发交付规范度**：100% 任务具备全链路状态机流转与操作人日志（Process Node Trace）；
- **越权拦截率**：代码级 5 层防错门禁对未授权跳步/越权实现 100% 拦截；
- **人工验收闭环**：代码合流前 100% 经人类用户显式验收，杜绝未经审阅的代码合流。

## 二、 他们怎么工作 (7 步标准研发工作流)

从收到业务需求到代码合流上线，目标用户的标准工作流拆解如下：

```
[步骤 1] 需求拆解与排期  (严经理 PM)
    ↓
[步骤 2] 架构设计与技术栈扫描 (钱架构 Architect)
    ↓
[步骤 3] 模块拆解与并行开发 (李开发 Dev / 马前端 Frontend) ── 受 WIP Limit 并发约束
    ↓
[步骤 4] 独立代码质量与安全审查 (周审查 Reviewer) ── 静态代码与规范审计
    ↓
[步骤 5] 全量用例与冒烟测试 (章测试 QA) ── 形成测试报告，交付至【已完成】
    ↓
[步骤 6] 人类用户核验与专属验收 (人类用户 USER) ── quick_task.py accept
    ↓
[步骤 7] Git 提交门禁与结项归档 (吕改特 DevOps / 李文通 Docs) ── verify_git_gate.py
```

## 四、 套件构成与安全确认门设计 (Skills + 安全机制)

### 1. 内部 Skills 构成
- **主技能**：`skills/yy-flow/`
  - 承载完整的 8 位专家子代理角色分配；
  - 调度 5 层防错门禁状态机引擎；
  - 提供 `/yy-flow`、`/yy-flow start`、`/yy-flow status`、`/yy-flow kanban` 等快捷命令。

### 2. 外部依赖与降级机制 (Zero-Speculation Fallback)
- **纯本地单机离线运行**：套件所有状态机、看板渲染与门禁脚本均为纯 Python 实现，**0 云端 API 依赖**，无网络或无外部 Connector 时 100% 独立平稳运行；
- **扩展支持**：可无缝对接企业内部钉钉群通知、飞书多维表格或 Jira（可选 Connector）。

### 3. 安全确认门设计 (严格契合白皮书原则四)
1. **状态机终态收敛至【已完成】**：AI Agent 自动化流转在测试通过后统一停留在【已完成】，严禁自主推进至【已验收】；
2. **【已验收】人类专属硬锁**：`validate_transition.py` 在状态机底层做物理权限判定，未携带 `delegated_by=USER` 授权的验收操作一律直接报错拦截；
3. **Pre-Commit Git 提交物理阻断**：提供 `verify_git_gate.py` 与 Pre-Commit 钩子，本地敲 `git commit` 时若存在尚未经人类验收的任务，直接物理终止提交。
