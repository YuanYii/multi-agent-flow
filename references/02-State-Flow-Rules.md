# 02 - 状态流转规则与打回不拆单规范

> 本规范定义任务在 8 个标准状态间的推进规则、打回处理约束与终态核验门控。  
> 跨角色提权代行与专家 Agent 间的消息总线 Context Payload 结构请强参阅：->  [`references/06-Inter-Agent-Handover-Protocol.md`](06-Inter-Agent-Handover-Protocol.md)

> **本文件说明**：定义任务生命周期的 8 个标准状态、7 类任务类型流转链、打回回退表与报告追加规范。

---

## 一、标准状态速查

| 状态 | 含义 | 下一合法状态 | 处理人 (Assignee) 规则 |
|------|------|-------------|-----------------------|
| **待开始** | 任务已建卡，等待领取或分配（<b>所有任务卡必须经历的状态</b>：--create 建卡 / 兜底自动建单均从此状态起步） | `进行中` / `已验收` | 保持为初始分配对象或设为自领取 DEV |
| **进行中** | 任务正在执行 | `审查中` / `已完成` / `已验收` / `已阻塞` | 当前执行者 |
| **审查中** | 开发完成，等待代码审查 | `测试中` / `已退回` | 改为 `REVIEWER` (代码) 或 `PM` (架构) |
| **测试中** | 审查通过，进行功能/系统测试 | `已完成` / `已退回` | 改为 `QA` |
| **已退回** | 审查/测试/验收未通过被打回 | `进行中` | 精确改回 **原负责人** (见回退表) |
| **已阻塞** | 遭遇依赖未就绪/环境中断 | `进行中` | 保持不变 |
| **已完成** | 工作完成，等待最终验收 | `已验收` / `已退回` | 改为 `PM` (到达已验收前必带 `结束时间`) |
| **已验收** | PM 验收通过 (最终终态) | (不可流转) | `严经理` (PM) |
| **已取消** | 任务作废/取消 (终态) | (不可流转) | `严经理` (PM) |

> **人员角色语义说明**：
> - **任务负责人 (Owner / 责任人)**：任务实际承接与主创开发者（如 `李开发`、`马前端`、`钱架构`），在任务整个生命周期内保持稳定不变。
> - **任务处理人 (Handler / 当前经办人)**：当前流转节点的操作责任人（如开发为 `李开发`，审查为 `周审查`，测试为 `章测试`，打回退回为原负责人 `李开发`，已完成/已验收/已取消等终态统一收敛为 `严经理`）。

### 流程节点双标识 (`{任务ID}-N{序号}`)

每次状态流转在看板卡片 `process` 字段追加结构化节点记录（说明可选、独立成行），行内嵌**全局唯一节点 ID**：

```text
[T0001-N03]  [2026-08-16 16:31:07]  状态由【审查中】更新至【测试中】，操作人: 章测试
操作说明: <可选的结构化说明文本>
```

- **节点 ID = 任务ID + 任务内节点序号**（如 `T0001-N03`），与缺陷编号 `DEF-T0084-1` 同构；
- 序号在 `board.json.seq.lock` 排他锁内取该卡 `max(N)+1` 分配：**单调递增、只追加、永不重排**；
- 回滚烧号不复用（回滚事件另行追加新节点行记录）；建单（`--create`）不占节点号——建卡是卡片诞生而非流程节点；
- 打回节点（`已退回`）正常占号，与缺陷编号 `DEF-{任务ID}-{轮次}` 相互独立、各行其是；
- 前端时间线按节点序号升序渲染，无节点标识的历史旧行保持原相对顺序排最前。

### 状态终态：【已取消 (CANCELLED)】规范与防物理删除

- **只增不减原则**：看板任务卡全生命周期只增不减，严禁物理删除或直接篡改底层 `board.json` 文件；
- **流转权限**：仅限 `PM (严经理)`（或由用户声明 `--delegated-by USER` 授权代行）将任务从任意合法状态（`待开始`/`进行中`/`审查中`/`测试中`/`已完成`/`已阻塞`/`已退回`）推进至【已取消】；
- **必填项与经办人收敛**：推进至【已取消】时，经办人（Assignee）必须收敛至 `严经理`，且必须携带 `end_time`（结束时间）与 `remarks`（取消原因说明）；
- **CLI 调用范例**：
  ```bash
  python3 scripts/quick_task.py complete \
    --task-id T00xx \
    --role PM \
    --from-status 进行中 \
    --to-status 已取消 \
    --assignee 严经理 \
    --end-time "$(date '+%Y-%m-%d %H:%M:%S')" \
    --remarks "【取消】需求变更/功能作废，经与用户确认不再执行"
  ```

## 二、统一入口网关与任务分级三问 (L0/L1/L2)

### 1. 统一入口双支线网关

所有调用本工作流的指令均经由统一网关处理：
- **控制台运维指令**（`start` / `status` / `kanban` / `sync-pr` / `gate`）：直通执行底层运维脚本，不产生多余前置分级；
- **业务研发与交互意图**：强制前置执行【分级三问】，并在回复首行显式声明 `【任务分级: L0/L1/L2】`。

### 2. 分级定义与机制映射

| 级别 | 判定标准 | 是否建卡 | 复用机制 | 状态流转链 | 典型示例 |
|---|---|---|---|---|---|
| **L0 即时问答** | 产出仅在当前会话内消费、无文件/仓库变更、不影响后续任务依据 | **否** | 不调用任何 CLI（无卡直答） | 会话直接作答 | “找一下文档规范”、“解释某个函数的含义”、“询问项目架构” |
| **L1 轻量任务** | 有真实交付物（单文件/文档/环境配置），单角色单步完成，无需代码审查与 QA 测试 | **是** | 类型 **B/C/D/F/G**（短链） | 待开始 → 进行中 → 已完成 → 已验收 (PM) | “更新 README 中的部署说明”、“修复配置文件路径”、“草稿整理” |
| **L2 标准任务** | 涉及业务核心代码、多角色协作（DEV→Reviewer→QA→PM）、公共库重构或其结论作为后续开发依据 | **是 (默认)** | 类型 **A**（全链） | 待开始 → 进行中 → 审查中 → 测试中 → 已完成 → 已验收 | “实现用户登录接口”、“重构订单状态机”、“前端页面开发” |

### 3. PM 派单分级三问决策流

```text
[业务需求输入]
   │
   ├─► 1. 会留下代码/文档/配置等仓库文件修改吗？
   │      ├─ 否 ──► 2. 结论需要作为后续工程依据事后追溯吗？
   │      │            ├─ 否 ───────────────► 【L0 即时问答】（无卡直接作答，0 毫秒 CLI 延迟，草稿入草稿箱）
   │      │            └─ 是 ───────────────► 【L1 轻量任务】（建卡走短链：B/C/D/F/G）
   │      │
   │      └─ 是 ──► 3. 需要多角色协作、修改业务核心代码或变更公共基础库吗？
   │                   ├─ 否 ───────────────► 【L1 轻量任务】（建卡走短链：单角色完成 → PM 严经理终态验收）
   │                   └─ 是 ───────────────► 【L2 标准研发任务】（建卡走全链：DEV 编码 → Reviewer 审查 → QA 测试 → PM 验收）
```

### 4. 核心红线与豁免机制

- **🛡️ 执行态 Task ID 豁免（防死循环建卡）**：若指令已显式携带 Task ID（如 `T0001`、`DEF-T0001-1`）或由子代理在执行内部流转（如提审、测试），**直接进入对应状态推进，严禁二次建卡**。
- **🔄 复合指令管道化**：若同时包含控制台操作与业务需求，优先执行控制台操作，随后将业务需求送入分级三问。
- **⚠️ 核心模块强制升格 L2**：涉及公共核心库、鉴权/安全、数据库迁移等关键变更，即使单文件修改亦**强制升格为 L2 全流程**。
- **硬红线 1（文件即锚点）**：任何涉及仓库文件创建、修改、删除的任务**必须建卡**，作为 Git 提交与工程审计的追溯锚点。
- **硬红线 2（结论即凭据）**：产出结论会被后续任务引用的**必须建卡**。
- **硬红线 3（用户显式指令）**：用户显式声明“建个任务”或指明 Task ID 的**必须建卡**。
- **反向红线（L0 无卡不违规）**：**L0 无卡不属于违规，绝不触发未建单违规拦截或孤儿巡检**。
- **L0 产出管理规则**：L0 过程产出严禁落入 `docs/D04-研发过程/D02-报告` 或 `docs/D04-研发过程/D01-任务`（避免触发孤儿巡检）；若确实产生临时草稿，应归档至 `docs/草稿箱/`，或升级为 L1 补录建卡。
- **L1 短链与 Fast-Track 的通道区别**：
  - **L1 短链**（B/C/D/F/G）：走标准短链，执行完成后推至 `已完成`，**必须由 PM 进行终态验收推至 `已验收`**；
  - **Fast-Track 特权通道**（带 `[HOTFIX]` 前缀）：属于紧急修复特权，允许执行方直接置为 `已完成/已验收`。

### 5. 缺省元数据（阶段 / 工作包 / WBS）自动推导规范

当用户/Agent 快速建卡未显式指定 `stage`、`wp`、`wbs` 时，系统自动执行标准化缺省推导，杜绝字段缺失阻断：
1. **阶段 (`stage`) 继承规范**：自动探测看板历史卡片，**继承最新/序号最大活跃阶段**（如已有 `S1`、`S2` 自动归入 `S2`；空看板时回退至 `S1 需求分析与系统架构设计`）；
2. **常规工作包 (`workpackage`) 规范**：自动归入该阶段的缺省常规工作包：`WP-{StageCode}-01 常规研发工作包`（如 `WP-S1-01 常规研发工作包`）；
3. **WBS 编号 (`wbs_id`) 编号规范**：自动生成三段式递增编号：`{StageNum}.1.{Seq}`（如阶段为 S1 时，第一张卡为 `1.1.1`，第二张为 `1.1.2`；S2 阶段为 `2.1.1`），完全适配阶段结项门禁核验。

## 三、7 类任务类型 (A-G) 差异化流转链

### 1. A 类 (开发任务：常规/AI)
```text
待开始 ──(DEV自领取)──> 进行中 ──(提交审查)──> 审查中(REVIEWER) ──(审查通过)──> 测试中(QA) ──(测试通过)──> 已完成(PM) ──(验收通过)──> 已验收
```

### 2. B 类 (架构设计任务)
```text
待开始 ──(PM分配)──> 进行中(ARCHITECT) ──(设计完成)──> 已完成(PM) ──(验收通过)──> 已验收
```

### 3. C 类 (文档任务) 与 D 类 (Git/运维任务)
```text
待开始 ──(PM分配)──> 进行中(DOCS/DEVOPS) ──(处理完成)──> 已完成(PM) ──(验收通过)──> 已验收
```

### 4. E 类 (用户自执行任务)
```text
待开始/进行中 (负责人=User) ──(PM直接确认)──> 已验收 (处理人=PM, 负责人=User)
```

### 5. F 类 (阶段总结任务)
```text
PM创建 ──> ARCHITECT/PM主笔撰写 ──> 已完成 ──> 已验收
```

### 6. G 类 (环境搭建/运行环境治理任务)
```text
待开始 ──(DEV自领取/PM分配)──> 进行中 ──(搭建完成)──> 已完成(PM) ──(验收通过)──> 已验收
```

## 四、打回规则与“打回不拆单”原则 ([WARN] 核心防错)

### 1. 各类型打回处理人回退表

| 打回触发点 | 任务类型 | 状态变更 | 处理人 (Assignee) 回退为 |
|-----------|---------|---------|-------------------------|
| 审查不通过 | A (开发/前端) / B (架构) | `审查中` → `已退回` | 原负责人 (DEV / FRONTEND / ARCHITECT) |
| 测试不通过 | A (开发/前端) | `测试中` → `已退回` | 原负责人 (DEV / FRONTEND) |
| 验收不通过 | A / B / G | `已完成` → `已退回` | 原负责人 (DEV / FRONTEND / ARCHITECT) |
| 验收不通过 | C (文档) | `已完成` → `已退回` | 原文档负责人 (DOCS) |
| 验收不通过 | D (Git/运维) | `已完成` → `已退回` | 原 DevOps 负责人 (DEVOPS) |

### 2. 打回不拆单原则（禁止派生孤儿任务）
- [FAILED] **禁止新建独立修复任务**：审查或测试不通过时，**严禁派生形如 `T0103-fix` 的新任务编号**。
- [SUCCESS] **原任务结构化打回**：一律在**原任务**上修改状态为 `已退回`，并在看板「备注」字段写入结构化缺陷信息：
  ```text
  缺陷编号：DEF-{原任务编号}-{轮次} (如 DEF-T0084-1)
  根因：导致审查/测试不通过的根因
  复现：稳定复现步骤或代码位置/规范条款
  修复建议：给开发者的具体修复指引
  ```

### 3. 报告追加原则（禁止新建独立复审/复测报告）
- 审查/测试退回修复后重新流转：
  - 开发任务报告：在原报告追加 **§9 返工/修订记录**；
  - 审查报告：在原审查报告追加 **§8 复审结论**；
  - 测试报告：在原测试报告追加 **§9 复测结论**；
- [FAILED] **严禁新建《XXX_复审报告.md》或《XXX_复测报告.md》等碎片文档**。
