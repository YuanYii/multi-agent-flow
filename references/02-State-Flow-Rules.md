# 02 - 状态流转规则与打回不拆单规范

> 本规范定义任务在 8 个标准状态间的推进规则、打回处理约束与终态核验门控。  
> 跨角色提权代行与专家 Agent 间的消息总线 Context Payload 结构请强参阅：->  [`references/06-Inter-Agent-Handover-Protocol.md`](06-Inter-Agent-Handover-Protocol.md)

> **本文件说明**：定义任务生命周期的 8 个标准状态、7 类任务类型流转链、打回回退表与报告追加规范。

---

## 一、标准状态速查

| 状态 | 含义 | 下一合法状态 | 处理人 (Assignee) 规则 |
|------|------|-------------|-----------------------|
| **待开始** | 任务已建卡，等待领取或分配（<b>所有任务卡必须经历的状态</b>：--create 建卡 / 兜底自动建单均从此状态起步） | `进行中` / `已验收` | 保持为初始分配对象或设为自领取 DEV |
| **进行中** | 任务正在执行 | `审查中` / `已完成` / `已验收` / `已阻塞` | 当前执行者 |
| **审查中** | 开发完成，等待代码审查 | `测试中` / `已退回` | 改为 `REVIEWER` (代码) 或 `PM` (架构) |
| **测试中** | 审查通过，进行功能/系统测试 | `已完成` / `已退回` | 改为 `QA` |
| **已退回** | 审查/测试/验收未通过被打回 | `进行中` | 精确改回 **原负责人** (见回退表) |
| **已阻塞** | 遭遇依赖未就绪/环境中断 | `进行中` | 保持不变 |
| **已完成** | 工作完成，等待最终验收 | `已验收` / `已退回` | 改为 `PM` (到达已验收前必带 `结束时间`) |
| **已验收** | PM 验收通过 (最终终态) | (不可流转) | `PM` |

### 流程节点双标识 (`{任务ID}-N{序号}`)

每次状态流转在看板卡片 `process` 字段追加结构化节点记录（说明可选、独立成行），行内嵌**全局唯一节点 ID**：

```text
[T0001-N03]  [2026-08-16 16:31:07]  状态由【审查中】更新至【测试中】，操作人: 章测试
操作说明: <可选的结构化说明文本>
```

- **节点 ID = 任务ID + 任务内节点序号**（如 `T0001-N03`），与缺陷编号 `DEF-T0084-1` 同构；
- 序号在 `board.json.seq.lock` 排他锁内取该卡 `max(N)+1` 分配：**单调递增、只追加、永不重排**；
- 回滚烧号不复用（回滚事件另行追加新节点行记录）；建单（`--create`）不占节点号——建卡是卡片诞生而非流程节点；
- 打回节点（`已退回`）正常占号，与缺陷编号 `DEF-{任务ID}-{轮次}` 相互独立、各行其是；
- 前端时间线按节点序号升序渲染，无节点标识的历史旧行保持原相对顺序排最前。

## 二、任务分级三问 (L0/L1/L2)

### 1. 分级定义与机制映射

| 级别 | 判定标准 | 是否建卡 | 复用机制 | 状态流转链 | 典型示例 |
|---|---|---|---|---|---|
| **L0 即时问答** | 产出仅在当前会话内消费、无文件/仓库变更、不影响后续任务依据 | **否** | 不调用任何 CLI（无卡直答） | 无 | “找一下文档规范”、“解释某个函数的含义”、“询问项目架构” |
| **L1 轻量任务** | 有真实交付物（单文件/文档/环境配置），单角色单步完成，无需代码审查与 QA 测试 | **是** | 类型 **B/C/D/F/G**（短链） | 待开始 → 进行中 → 已完成 → 已验收 (PM) | “更新 README 中的部署说明”、“修复配置文件路径”、“草稿整理” |
| **L2 标准任务** | 涉及业务核心代码、多角色协作（DEV→Reviewer→QA→PM）、其结论作为后续开发依据 | **是 (默认)** | 类型 **A**（全链） | 待开始 → 进行中 → 审查中 → 测试中 → 已完成 → 已验收 | “实现用户登录接口”、“重构订单状态机”、“前端页面开发” |

### 2. PM 派单分级三问决策流

```text
[新任务输入]
   │
   ├─► 1. 会留下文件/仓库修改吗？
   │      ├─ 否 ──► 2. 结论需要作为后续依据事后追溯吗？
   │      │            ├─ 否 ───────────────► 【L0 即时问答】（无卡直接作答）
   │      │            └─ 是 ───────────────► 【L1 轻量任务】（建卡走短链）
   │      │
   │      └─ 是 ──► 3. 需要多角色协作或修改业务核心代码吗？
   │                   ├─ 否 ───────────────► 【L1 轻量任务】（建卡走短链：B/C/D/F/G）
   │                   └─ 是 ───────────────► 【L2 标准任务】（建卡走全链：A 类）
```

### 3. 核心红线与反向豁免

- **硬红线 1（文件即锚点）**：任何涉及仓库文件创建、修改、删除的任务**必须建卡**，作为 Git 提交与工程审计的追溯锚点。
- **硬红线 2（结论即凭据）**：产出结论会被后续任务引用的**必须建卡**。
- **硬红线 3（用户显式指令）**：用户显式声明“建个任务”或指明 Task ID 的**必须建卡**。
- **反向红线（L0 无卡不违规）**：**L0 无卡不属于违规，绝不触发未建单违规拦截或孤儿巡检**。
- **L0 产出管理规则**：L0 过程产出严禁落入 `docs/04-研发过程/报告` 或 `docs/04-研发过程/任务`（避免触发孤儿巡检）；若确实产生临时草稿，应归档至 `docs/草稿箱/`，或升级为 L1 补录建卡。
- **L1 短链与 Fast-Track 的通道区别**：
  - **L1 短链**（B/C/D/F/G）：走标准短链，执行完成后推至 `已完成`，**必须由 PM 进行终态验收推至 `已验收`**；
  - **Fast-Track 特权通道**（带 `[HOTFIX]` 前缀）：属于紧急修复特权，允许执行方直接置为 `已完成/已验收`。

## 三、7 类任务类型 (A-G) 差异化流转链

### 1. A 类 (开发任务：常规/AI)
```text
待开始 ──(DEV自领取)──> 进行中 ──(提交审查)──> 审查中(REVIEWER) ──(审查通过)──> 测试中(QA) ──(测试通过)──> 已完成(PM) ──(验收通过)──> 已验收
```

### 2. B 类 (架构设计任务)
```text
待开始 ──(PM分配)──> 进行中(ARCHITECT) ──(设计完成)──> 已完成(PM) ──(验收通过)──> 已验收
```

### 3. C 类 (文档任务) 与 D 类 (Git/运维任务)
```text
待开始 ──(PM分配)──> 进行中(DOCS/DEVOPS) ──(处理完成)──> 已完成(PM) ──(验收通过)──> 已验收
```

### 4. E 类 (用户自执行任务)
```text
待开始/进行中 (负责人=User) ──(PM直接确认)──> 已验收 (处理人=PM, 负责人=User)
```

### 5. F 类 (阶段总结任务)
```text
PM创建 ──> ARCHITECT/PM主笔撰写 ──> 已完成 ──> 已验收
```

### 6. G 类 (环境搭建/运行环境治理任务)
```text
待开始 ──(DEV自领取/PM分配)──> 进行中 ──(搭建完成)──> 已完成(PM) ──(验收通过)──> 已验收
```

## 四、打回规则与“打回不拆单”原则 ([WARN] 核心防错)

### 1. 各类型打回处理人回退表

| 打回触发点 | 任务类型 | 状态变更 | 处理人 (Assignee) 回退为 |
|-----------|---------|---------|-------------------------|
| 审查不通过 | A (开发/前端) / B (架构) | `审查中` → `已退回` | 原负责人 (DEV / FRONTEND / ARCHITECT) |
| 测试不通过 | A (开发/前端) | `测试中` → `已退回` | 原负责人 (DEV / FRONTEND) |
| 验收不通过 | A / B / G | `已完成` → `已退回` | 原负责人 (DEV / FRONTEND / ARCHITECT) |
| 验收不通过 | C (文档) | `已完成` → `已退回` | 原文档负责人 (DOCS) |
| 验收不通过 | D (Git/运维) | `已完成` → `已退回` | 原 DevOps 负责人 (DEVOPS) |

### 2. 打回不拆单原则（禁止派生孤儿任务）
- [FAILED] **禁止新建独立修复任务**：审查或测试不通过时，**严禁派生形如 `T0103-fix` 的新任务编号**。
- [SUCCESS] **原任务结构化打回**：一律在**原任务**上修改状态为 `已退回`，并在看板「备注」字段写入结构化缺陷信息：
  ```text
  缺陷编号：DEF-{原任务编号}-{轮次} (如 DEF-T0084-1)
  根因：导致审查/测试不通过的根因
  复现：稳定复现步骤或代码位置/规范条款
  修复建议：给开发者的具体修复指引
  ```

### 3. 报告追加原则（禁止新建独立复审/复测报告）
- 审查/测试退回修复后重新流转：
  - 开发任务报告：在原报告追加 **§9 返工/修订记录**；
  - 审查报告：在原审查报告追加 **§8 复审结论**；
  - 测试报告：在原测试报告追加 **§9 复测结论**；
- [FAILED] **严禁新建《XXX_复审报告.md》或《XXX_复测报告.md》等碎片文档**。
